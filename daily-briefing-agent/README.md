# 题目：每日简报生成器

## 背景

我们正在做一款"早晨陪你出门"的语音助手。用户每天起床后，戴上耳机听一段 **60–90 秒**的个性化早间简报，内容由 Agent 系统从用户当日数据中生成。

这道题考察的是你**设计 Agent 系统、与 LLM 协作并交付一个端到端可运行原型**的能力。我们不在意你是否使用某个特定框架，但在意你的设计取舍以及最终输出质量。

**预期用时：约 2 小时**（包含设计、实现、自测、文档）。

**允许且鼓励使用任何 AI 工具完成。** 我们看的是你最终交付了什么、以及你如何指挥 AI 协助你完成。如何使用 AI 本身就是这道题的考察点之一。

---

## 任务

实现一个 Agent 系统，读取 `inputs/` 中的四份 JSON 数据，生成两个文件：

1. **`briefing.txt`** — 朗读用文本（给 TTS 用）
2. **`briefing.json`** — 结构化 metadata（说明这段简报涵盖了哪些 item、估计朗读时长、章节切分）

放在项目根目录即可。

---

## 输入数据

所有输入位于 `inputs/` 下，均为 JSON。**用户的母语和数据语言均为英文**，简报输出也用英文。

| 文件 | 内容 | 量级 |
|---|---|---|
| `profile.json` | 用户偏好：感兴趣 / 不感兴趣的话题、关注的实体、语气偏好、目标时长 | 1 个 user 对象 |
| `calendar.json` | 今天（2026-05-15，周五）的日程 | 11 个事件 |
| `emails.json` | 过去 24 小时的邮件摘要（已经过初步清洗，含 `labels` 字段） | 20 封 |
| `news.json` | RSS 抓取的新闻条目摘要 | 30 条 |

数据中存在一些**真实世界里常见的小复杂情况**（例如：日程冲突、不同来源对同一事件的报道、用户偏好里的细微例外、被标记为 private 的事件、含 action-required 的邮件、需去重的信息）。我们希望看到你的 Agent 系统如何处理它们——但不要求"全部完美处理"，**请在 DECISIONS.md 里写清你的取舍**。

---

## 交付物

请在你提交的目录里包含以下文件：

```
your-submission/
├── briefing.txt              # 朗读用纯文本
├── briefing.json             # 结构化 metadata
├── DECISIONS.md              # 设计文档（必交）
├── README.md                 # 如何运行你的代码
└── <你的源码 / 脚手架>        # 技术栈不限
```

### `briefing.txt` 要求

- **纯文本**，给 TTS 朗读用
- **不要出现 Markdown 标记**（`#`、`*`、列表符号等）
- **不要出现 URL 或邮箱地址**
- **数字与单位口语化**：写 `"twelve percent"` 不写 `"12%"`，`"two hundred thousand dollars"` 不写 `"$200K"`
- 目标朗读时长 60–90 秒（用户的 `profile.json` 里有偏好值）
- 不要每天用同样的开头（profile 里有此要求）

### `briefing.json` 要求

至少包含以下字段，**字段命名你可以自己定**，但要在 DECISIONS.md 里说明：

- 这段简报覆盖了哪些 input item 的 `id`（calendar / email / news 各自）
- 你估算的朗读时长（秒）+ 估算方法
- 章节切分（如：开场 / 今日日程 / 邮件要点 / 新闻 / 收尾），每段对应到 `briefing.txt` 里的字符或行范围
- 哪些 item 被**主动丢弃**了，以及丢弃理由（这一项尤其重要，让我们能看到你的过滤逻辑）

### `DECISIONS.md` 要求（必交）

我们用模板 `DECISIONS.template.md` 给了你一个起点。至少包含：

1. **架构图**（ASCII / Mermaid / 手画拍照都可以）
2. **关键设计决策**：你的 Agent 是单步 prompt 还是多步？为什么？怎么排序与去重？怎么控制时长？如何让输出尊重 profile？
3. **AI 工具使用记录**：你让 AI 做了什么、哪里你主导、哪里 AI 出错你是怎么发现并纠正的——**这是加分项，不写不扣分，但写得好我们会非常欣赏**
4. **已知限制 / 没来得及做的事**

## 约束与建议

- **技术栈不限**：Python / TypeScript / Go / 用 n8n 拖出来都可以。能跑、有源码即可。
- **API 不限**：可以用 Anthropic / OpenAI / 本地模型 / 任意 SDK。如果用到了 API key，请用环境变量，不要把 key 提交进来。
- **运行说明必须清晰**：我们应该能在 5 分钟内按你的 README 跑通你的代码。
- **不要伪造输入**：请使用我们提供的 `inputs/` 原样跑出结果。可以加自己的测试数据另存，但提交的 `briefing.txt` / `briefing.json` 必须基于原始数据生成。

## 评分维度（公开 rubric）

我们会从以下几个角度看你的提交，**不存在标准答案**：

| 维度 | 我们在看什么 |
|---|---|
| **Agent 设计** | 你是怎么拆任务的？多步 / 单步？为什么？是否使用了工具调用、结构化输出、分支判断？能否扩展到更多输入？ |
| **对 profile 的尊重** | 简报里有没有违反用户偏好（出现了"不感兴趣"的话题、没出现"必须包含"的实体）？语气是否贴合？ |
| **信息筛选与去重** | 30 条新闻、20 封邮件里，真正进入简报的是不是最该进的那些？同一事件的多个来源是否合理整合？ |
| **TTS 友好度** | `briefing.txt` 朗读起来自然吗？数字/单位/缩写是否口语化？有没有 markdown 痕迹？ |
| **DECISIONS.md 质量** | 你的取舍是不是清晰、有理由？你和 AI 的协作过程是不是真实可见？我们更喜欢"诚实写出 trade-off"，而不是"假装一切完美"。 |
| **工程基础** | 代码能否一次跑通？有没有错误处理？输出是否稳定可重复？ |

我们**不**用以下标准来评判：

- 你的源码行数 / 是否封装得很优雅（这是 2 小时的活，不要过度设计）
- 你用没用我们家某个特定的 SDK / 模型
- briefing 的"创意程度"——我们要的是恰当、不是惊艳

## 一些善意的提示

- **先读一遍数据再动手**。`inputs/` 里有几个故意埋的小情况，5 分钟扫一遍数据可能让你在设计阶段少走弯路。
- **不要让 AI 替你思考架构**。AI 写代码很快，但 Agent 系统的设计判断（拆几步、用什么提示词、怎么处理边界）最好你自己想清楚再让它实现。
- **60–90 秒很短**。打开手机录音读一下你的 `briefing.txt`，看是不是真的能在时间内读完。
- **DECISIONS.md 不要写成"项目报告"**，写成你给同事的口头交接：诚实、具体、有取舍。

祝你做得开心。
